# M5.3 Role Hierarchy Decision Audit

**Scope:** Read-only architecture investigation.  
**Date:** 2026-07-26  
**Objective:** Define the correct role authority model for Q360 before implementing role hierarchy utilities.

---

## 1. Current Role Vocabulary

### 1.1 Canonical role type
File: `src/types/user.ts:1`

```typescript
export type UserRole = 'user' | 'owner' | 'admin' | 'manager' | 'waiter' | 'cashier' | 'kitchen' | 'staff';
```

### 1.2 Role storage locations

| Table | Column | Context |
|-------|--------|---------|
| `users` | `role` (text, default `'user'`) | Platform/Business-level identity |
| `staffMembers` | `role` (text, not null) | Workspace/operational assignment |
| `staffInvitations` | `role` (text, not null) | Pending invitation role |

### 1.3 Role vocabulary in use

**Platform role:**
- `admin` — Platform operator. Access to `/admin/*` routes only (`admin.ts:16`).

**Business/Tenant roles (users table):**
- `owner` — Business owner. Can claim ownership, manage all business settings.
- `user` — Generic unassigned user. May be a legacy restaurant creator eligible for `owner` upgrade.

**Workspace/Operational roles (staffMembers table):**
- `manager` — Can manage staff, inventory, bookings, Q usage.
- `waiter` — Floor service. Can create orders, update bookings, manage tables.
- `cashier` — Payment handling. Can record payments, create pay-now orders.
- `kitchen` — Kitchen staff. Can mark orders ready.
- `staff` — Generic staff. Used in retail orders and some shared surfaces.

## 2. Current Role Hierarchy Evidence

### 2.1 The `requireRole()` middleware
File: `backend/src/middleware/auth.ts:118–133`

```typescript
export const requireRole = (allowedRoles: string[]) => {
    return async (c: Context<AppEnv>, next: Next) => {
        const userRole = c.get('userRole');
        if (!userRole || !allowedRoles.includes(userRole)) {
            return c.json({ error: 'Forbidden: Insufficient permissions' }, 403);
        }
        await next();
    };
};
```

**Verdict:** `requireRole()` performs **exact string matching only**. There is NO hierarchy enforcement in the generic middleware.

**Evidence of intended hierarchy (not implemented):**
> "Owner/Admin always have access? Or strict check?"  
> "for hierarchy: Owner > Admin > Manager > Staff > Viewer"
> — `auth.ts:122–126` (comments only)

### 2.2 Restaurant domain role lists
File: `backend/src/services/restaurantDomain.ts:37–40`

```typescript
const waiterRoles = ['waiter', 'manager', 'owner', 'admin'] as const;
const kitchenRoles = ['kitchen', 'manager', 'owner', 'admin'] as const;
const paymentRoles = ['cashier', 'manager', 'owner', 'admin'] as const;
const orderCancelRoles = ['waiter', 'cashier', 'manager', 'owner', 'admin'] as const;
```

**Verdict:** `restaurantDomain.ts` implements **domain-specific role lists** for action permissions. This is the closest thing to a hierarchy — each action defines its own allowed roles. However, it is still exact-match (via `hasRole()`), not a true hierarchy.

### 2.3 Q Assistant role checks
File: `backend/src/routes/restaurant.ts:844–850`

```typescript
const canUseQ = (actor: RestaurantActor) => (
    actor.role === 'owner' || actor.role === 'admin' || actor.role === 'manager' || isLegacyRestaurantOwnerCompatible(actor)

    actor.role === 'owner' || actor.role === 'admin' || isLegacyRestaurantOwnerCompatible(actor)
```

**Verdict:** Q access is hardcoded with explicit role checks. `manager` can use Q but cannot review drafts.

### 2.4 Frontend role assumptions
File: `src/utils/restaurantAccess.ts:3–4`


**⚠️ CRITICAL FINDING:** The frontend includes `'user'` in `BUSINESS_MANAGEMENT_ROLES`. This means any `user`-role account is treated as a manager in the frontend module access check.

## 3. Conflicts Between Exact-Match Checks and Hierarchy Expectations

### 3.1 Conflict map

| Location | Pattern | Hierarchy Expected? | Actual Behavior |
|----------|---------|---------------------|-----------------|
| `auth.ts:requireRole()` | Exact match in array | Yes (comments say so) | No hierarchy |
| `restaurantDomain.ts:hasRole()` | Exact match in array | Partial (domain lists) | Exact match only |
| `restaurant.ts:canUseQ()` | Explicit `===` checks | Yes | Hardcoded explicit |
| `restaurant.ts:booking routes` | `canUseQ \|\| waiter` | Yes | Explicit only |
| `admin.ts` | `requireRole(['admin'])` | No (platform only) | Exact match |
| `staff.ts` | `requireRole(['user','owner','admin','manager'])` | Partial | `user` can invite staff |
| `inventory.ts` | `requireRole(['user','owner','admin','manager'])` | Partial | `user` can manage stock |
| `customers.ts` | `requireRole(['owner','admin','manager'])` | Partial | `user` excluded |
| `orders.ts` | `requireRole(['owner','admin','manager','staff'])` | Partial | `waiter`/`cashier` excluded |

### 3.2 Key conflicts discovered

**A. `user` role inconsistency**
- `inventory.ts` allows `user` to create/update stock
- `customers.ts` does NOT allow `user` to create customers
- `staff.ts` allows `user` to invite staff members
- `restaurant.ts` bookings allow `waiter` but not `user`

**B. `staff` vs operational roles**
- `orders.ts` (retail/generic) allows `staff` to create orders
- `restaurant.ts` (restaurant POS) uses `waiter`/`cashier`/`kitchen` — never `staff`
- `staff.ts` allows `user`/`owner`/`admin`/`manager` to invite, but invited roles are `manager`/`waiter`/`cashier`/`kitchen`/`staff`

**C. `admin` ambiguity**
- Platform `admin` = access to `/admin/*` routes
- But `restaurantDomain.ts` includes `'admin'` in `waiterRoles`, `kitchenRoles`, `paymentRoles` — treating platform admin as super-user inside workspaces
- This conflates **platform admin** with **workspace admin**

## 4. Legacy Owner Handling

### 4.1 The legacy owner pattern
File: `backend/src/services/businessOwnership.ts:11–50`

```typescript
const isLegacyRestaurantCreator = (user) => (
    user.role === 'user' &&
    user.userType === 'sme' &&
    user.segment === 'restaurant' &&
    user.onboardingCompleted === true &&
    user.primaryWorkspace === '/app/restaurant'
);
```

### 4.2 Runtime role elevation
`resolveEffectiveBusinessRole()`:
1. If `tokenRole !== 'user'`, returns token role immediately
2. If `users.role !== 'user'`, returns stored role
3. If `businesses.ownerUserId === userId`, upgrades `users.role` to `'owner'` in DB and returns `'owner'`
4. If no owner set and user is a legacy restaurant creator with no staff membership, claims ownership and upgrades to `'owner'`

**Verdict:** Legacy owners are **runtime-elevated** from `'user'` to `'owner'`. This means:
- The `users.role` column may still say `'user'` for some owners
- `authMiddleware` resolves the effective role per-request via `resolveEffectiveBusinessRole()`
- Frontend receives the elevated role in the JWT token

### 4.3 Legacy owner compatibility in restaurant domain
File: `backend/src/services/restaurantDomain.ts:45–58`

`isLegacyRestaurantOwnerCompatible()` checks the full legacy creator profile and grants equivalent permissions to `'owner'`.

**Verdict:** Restaurant domain has **dual authorization paths**: explicit role check OR legacy owner compatibility. This is a necessary backward-compatibility mechanism but creates authorization surface area.

## 5. Recommended Canonical Role Hierarchy

### 5.1 Proposed hierarchy

```
Platform Layer (cross-tenant)
├── platform_admin  [new — currently 'admin' in users table]
│   └── Full platform access (/admin/*, user/business management)
│
Tenant Layer (business-scoped)
├── owner
│   └── Full business management, Q draft review, staff invitation, settings
├── admin  [workspace — currently conflated with platform admin]
│   └── Business management minus ownership transfer
├── manager
│   └── Staff management, inventory, bookings, Q usage, reports
│
Operational Layer (workspace-scoped)
├── waiter
│   └── Table management, order creation, booking creation
├── cashier
│   └── Payment recording, pay-now orders, collection
├── kitchen
│   └── KDS ticket lifecycle, mark ready
└── staff
    └── Generic operational (retail orders, shared surfaces)
```

## 6. Roles That Are Platform-Wide vs Workspace-Specific

### 6.1 Current classification

| Role | Current Scope | Correct Scope | Issue |
|------|--------------|---------------|-------|
| `admin` (users.role) | Both platform AND workspace | Should be split | Platform admin can act as workspace admin in restaurant domain |
| `owner` (users.role) | Business/Tenant | Business/Tenant | ✅ Correct |
| `user` (users.role) | Business/Tenant | Should be deprecated | Ambiguous; legacy owner trap |
| `manager` (staffMembers.role) | Workspace | Workspace | ✅ Correct |
| `waiter` (staffMembers.role) | Workspace | Workspace | ✅ Correct |
| `cashier` (staffMembers.role) | Workspace | Workspace | ✅ Correct |
| `kitchen` (staffMembers.role) | Workspace | Workspace | ✅ Correct |
| `staff` (staffMembers.role) | Workspace | Workspace | ✅ Correct |

### 6.2 The `admin` conflation problem

**Evidence:**
- `admin.ts:16`: `requireRole(['admin'])` gates platform routes
- `restaurantDomain.ts:37–40`: `'admin'` is included in `waiterRoles`, `kitchenRoles`, `paymentRoles`
- `usersPage.tsx:113`: Admin can be assigned to any business
- `Sidebar.tsx:76`: `user?.role === 'admin'` shows Platform Console link

**Verdict:** The same `'admin'` string represents **two different authorities**:
1. **Platform admin** — cross-tenant, accesses `/admin/*`
2. **Workspace super-user** — inside restaurant domain, can perform any action

**Risk:** A platform admin assigned to a business could accidentally be treated as a workspace admin inside that business's routes.

## 7. Risks Before Implementation

### 7.1 Risk register

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Implementing hierarchy breaks exact-match routes | High | High | Audit every `requireRole()` call before changing behavior |
| `user` role frontloaded as management | Medium | High | Fix `restaurantAccess.ts` first; review all `user` in allowed arrays |
| `admin` conflation causes privilege escalation | Medium | Critical | Separate platform_admin from workspace roles before hierarchy |
| Legacy owner runtime elevation incompatible with hierarchy | Medium | High | Ensure `resolveEffectiveBusinessRole()` runs before hierarchy check |
| Frontend/backend role assumptions diverge | High | Medium | Align `restaurantAccess.ts` with backend `restaurantDomain.ts` |
| Staff invitation allows assigning platform roles | Low | High | Validate invitation role against staff-only allowlist |

### 7.2 Most dangerous pattern

```typescript
// restaurantAccess.ts:3
const BUSINESS_MANAGEMENT_ROLES = new Set<UserRole>(['user', 'owner', 'admin', 'manager']);
```

This treats `'user'` as a management role. If a hierarchy utility is built on this assumption, every generic user gains manager-level frontend access.

## 8. Safest M5.3 Implementation Boundary

### 8.1 What M5.3 should NOT do
- Do NOT modify `requireRole()` to implement hierarchy yet
- Do NOT create a generic `hasPermission()` utility yet
- Do NOT split `admin` into `platform_admin` / `workspace_admin` yet
- Do NOT remove legacy owner handling
- Do NOT change schema or add role tables

### 8.2 What M5.3 CAN do safely
1. **Document** the canonical hierarchy (this audit)
2. **Freeze** the role vocabulary — no new roles without ADR approval
3. **Align** `restaurantAccess.ts` with backend reality:
   - Remove `'user'` from `BUSINESS_MANAGEMENT_ROLES`
   - Document why each role is/is not management
4. **Audit** every `requireRole()` call and map to the intended hierarchy
5. **Add comments** to `auth.ts` clarifying that `requireRole()` is exact-match only

### 8.3 Recommended immediate fix (within M5 hardening scope)
File: `src/utils/restaurantAccess.ts:3`

```typescript
// BEFORE (incorrect)
const BUSINESS_MANAGEMENT_ROLES = new Set<UserRole>(['user', 'owner', 'admin', 'manager']);

// AFTER (corrected)
const BUSINESS_MANAGEMENT_ROLES = new Set<UserRole>(['owner', 'admin', 'manager']);
```

**Rationale:** `'user'` is not a management role. It is either:
- A legacy restaurant creator (elevated to `owner` at runtime)
- A staff member who should have `staffMembers.role` instead
- An unassigned account that should not have module access

### 8.4 What future milestones should do
- **M6+:** Implement `requireHierarchyRole(['manager'])` that implicitly includes `owner`/`admin`
- **M7+:** Separate `platform_admin` from workspace roles (requires schema discussion)
- **M8+:** Deprecate `'user'` as a business role; migrate to `owner` or operational role
