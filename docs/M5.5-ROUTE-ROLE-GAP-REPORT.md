# M5.5 — Route Role Gap Report

**Status:** READ-ONLY audit output. Documentation only. No code, role, auth, or schema changes.
**Date:** 2026-07-26
**Scope:** All `requireRole()` call sites and role checks across `backend/src/routes/`, plus legacy owner behavior and M6 preparation.

---

## 1. 角色判定机制（审计基准）

- `requireRole()`（`middleware/auth.ts:118`）：**精确匹配**，无层级。注释里写着层级设想（Owner > Admin > Manager > Staff），但实现是 `allowedRoles.includes(userRole)`。
- `authMiddleware` 每次请求从 DB 重读 `users.role`（锁定/停用即时生效），再经 `resolveEffectiveBusinessRole()` 写入 `c.userRole`。
- `restaurant.ts` 不用 `requireRole()`，改用自建的 `restaurantActorFor()` + `canUseQ()` + `canPerformRestaurantAction()`（`services/restaurantDomain.ts`）两套体系并存。

## 2. requireRole() 全部调用点

| 文件 | 位置 | 允许角色 | 保护的路由 |
|---|---|---|---|
| admin.ts:16 | `use('*')` | `admin` | 平台管理全部路由 |
| purchasesExpenses.ts:13 | `use('*')` | `owner, admin` | 采购/支出全部路由 |
| inventory.ts:36, 85, 175 | 3 处写操作 | `user, owner, admin, manager` | 库存调整/新建/编辑 |
| suppliers.ts:16, 34, 62, 82 | 4 处写操作 | `user, owner, admin, manager` | 供应商与采购单 |
| staff.ts:12, 13, 19 | list/invite/patch | `user, owner, admin, manager` | 员工列表、邀请、编辑 |
| customers.ts:59, 98 | 2 处写操作 | `owner, admin, manager` | 客户新建/编辑 |
| quotes.ts:210, 271 | 2 处写操作 | `owner, admin, manager` | 报价单新建/编辑 |
| orders.ts:42 | POST /orders | `owner, admin, manager, staff` | 通用订单创建 |
| business.ts:12 | `EDIT_ROLES`（非 requireRole，自建 canEdit） | `user, owner, admin, manager` | 业务设置写操作 |

restaurant.ts 内部角色矩阵（restaurantDomain.ts）：
- `waiterRoles` = waiter, manager, owner, admin（下单、送达）
- `kitchenRoles` = kitchen, manager, owner, admin（mark_ready）
- `paymentRoles` = cashier, manager, owner, admin（收款、pay-now、collected）
- `orderCancelRoles` = waiter, cashier, manager, owner, admin（waiter/cashier 有单状态与归属的二次限制；kitchen 显式禁止取消）
- `canUseQ` = owner, admin, manager + legacy owner（Q Assistant、菜单管理、桌台管理）

## 3. 平台 admin vs 业务 admin 冲突（M6 最大风险点）

**`admin` 单一角色被两个完全不同的安全域共用：**

1. `admin.ts:16` `requireRole(['admin'])` —— 注释自称 "Platform administration"，但检查的就是 `users.role === 'admin'`。
2. 所有业务路由（inventory、staff、quotes、purchasesExpenses、restaurantDomain 的所有角色数组）也把 `admin` 当作**业务管理员**放行。

后果：任何一个业务 admin 同时是平台 admin（可访问 /admin/stats、用户管理、系统设置等跨租户面）；反过来平台 admin 对所有租户业务数据有全权。两个域之间**没有任何隔离机制**，这正是 M6 "Separate platform_admin from workspace admin" 必须解决的问题。

## 4. 缺失与不一致的检查

**A. `'user'` 角色在写路由中的不一致（M5.3/M5.4 已预示）：**
- 含 `user`：inventory(3)、suppliers(4)、staff(3)、business.EDIT_ROLES
- 不含 `user`：customers、quotes、orders、purchasesExpenses
- 同一语义的"业务管理写操作"两种口径并存。`staff.post('/invite')` 允许 `user` 意味着任何已认证个人用户（非 legacy owner）理论上可邀请员工——依赖 legacy owner 判定在别处兜底，属于隐性依赖。

**B. restaurant.ts 的 GET 端点零角色检查**（仅 authMiddleware）：
- `GET /business-pulse/snapshot`（1082）— 经营快照，含未付订单、畅销品数据，**任何已认证用户可读**，而同族的 `/business-pulse`、`/q/*` 全部要求 `canUseQ`。
- `GET /menu`（1506）、`GET /tables`（1753）、`GET /orders`（2570）、`GET /reports/daily`（2613）、`GET /reports/summary`（2707）、`GET /kds`（3047）、`GET /dashboard`（3182）— 财务报表和经营数据对 waiter/kitchen/cashier/任意 `user` 全部开放。**日报与汇总报表开放给厨房角色是明显的过度暴露**。

**C. bookings 端点角色不对称：**
- `GET /bookings`（1759）无角色检查（仅 tables 模块开关）；POST/PATCH/桌台状态更新要求 `canUseQ || waiter`。读与写口径不一致。

**D. 模块启用检查（isBusinessModuleEnabled）只覆盖两个文件**：business.ts、restaurant.ts（tables 模块）。inventory、staff、customers、purchasesExpenses、suppliers、quotes 这些可配置模块路由**没有任何 `isBusinessModuleEnabled()` 检查**，也没有 `moduleAccess` 校验——M5.6 的主要缺口在此得到确认。

**E. orders.ts（通用订单）允许 `staff` 角色**，而 restaurant.ts 体系里 `staff` 不出现在任何操作角色数组中——两套路由对同一角色语义不同。

## 5. Legacy owner 行为

两条独立路径，目前都正常但属双份维护：
- `resolveEffectiveBusinessRole()`（authMiddleware 内）：DB 中 `role='user'` 的 legacy 创建者被提升为 `owner` 并**回写 DB**（含抢占 `ownerUserId` 的副作用——员工身份优先，防冒领设计正确）。
- `isLegacyRestaurantOwnerCompatible()`（restaurantDomain.ts）：不提升 DB，仅在请求内放行（要求 sme/restaurant/onboarded/primaryWorkspace 五项全中）。

注意：authMiddleware 的提升先发生，所以 restaurant.ts 的 `isLegacyRestaurantOwnerCompatible` 实际只在提升失败或用户不匹配时兜底。M5.4 从前端 `BUSINESS_MANAGEMENT_ROLES` 移除 `'user'` 后，legacy owner 仍靠后端提升路径工作，行为冻结要求可以满足——但 M6 若改 `requireRole` 语义必须保留此提升。

## 6. M6 最安全准备建议

1. **先拆分 admin 域**：引入 `platform_admin` 之前，admin.ts 是唯一只认 `admin` 的文件——改动面最小，可先行。
2. **requireHierarchyRole() 落地前必须先决策 `'user'`**：当前含 `user` 的 11 个调用点若在层级模型中把 `user` 排在最低位，会静默扩大访问；建议 M6 第一步是把这 11 处显式改为目标角色集，再引入层级中间件。
3. **读端点分级**：把 `reports/daily`、`reports/summary`、`business-pulse/snapshot`、`dashboard` 归入管理层可读，作为 M6 层级映射的第一批受益者。
4. **restaurantDomain 角色数组是唯一干净的角色矩阵**，可直接迁移为层级常量的种子数据（waiterRoles/kitchenRoles/paymentRoles/orderCancelRoles）。
5. **保持 `requireRole()` 精确匹配语义不动**（ADR 冻结要求），新层级走新函数 `requireHierarchyRole()`，逐路由迁移、可回滚。
6. **冻结项**：legacy owner 提升路径与五项判定条件在 M6 中必须原样保留，否则存量账户立即失权。
