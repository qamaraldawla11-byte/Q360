# M5.2 Booking Capability Decision Audit

**Scope:** Read-only architecture investigation.  
**Date:** 2026-07-26  
**Objective:** Determine correct ownership of Booking capability — Restaurant-specific or future Booking Core.

---

## 1. Current Booking Ownership

### 1.1 Schema Ownership
- Table: `restaurantBookings` (`backend/src/db/schema.ts:185–216`)
- Columns: `businessId`, `customerId`, `customerName`, `partySize`, `startsAt`, `endsAt`, `tableIds` (jsonb), `status` (enum: pending/confirmed/arrived/seated/completed/cancelled/no_show), `occasion`, `notes`, `depositAmount`, `createdBy`, `updatedBy`
- Companion table: `restaurantTables` (`schema.ts:217–228`)
- **Verdict:** Schema is `restaurant_` prefixed. Booking data is physically coupled to Restaurant tenant tables.

### 1.2 Route Ownership
- File: `backend/src/routes/restaurant.ts`
- Routes:
  - `GET /restaurant/bookings` — line 1759
  - `POST /restaurant/bookings` — line 1778
  - `PATCH /restaurant/bookings/:id` — line 1832
- **All three routes gate on `isBusinessModuleEnabled(..., 'tables')`** (lines 1760, 1779, 1833).
- There is **no `booking` policy key**. Bookings are a subordinate capability of the `tables` module.

### 1.3 Frontend Ownership
- File: `src/modules/commerce/restaurant/views/FloorView.tsx`
- The Floor view contains **both** live table status management **and** reservation creation/management UI.
- Route: `/app/restaurant/floor` (moduleRegistry: `tables` moduleKey)
- No dedicated `/app/restaurant/bookings` route exists.

### 1.4 Q Assistant Ownership
- `buildQBusinessBriefing()` (`restaurant.ts:641`) queries `restaurantBookings` directly.
- Q draft type `booking_brief` exists (`restaurant.ts:159, 853`).
- Q provisioning (`qGuestBriefProvisioning.ts`) does **not** create booking data; it only creates tables.
- Q context builder references bookings through Restaurant-specific evidence types.

## 2. Restaurant-Specific Behavior

### 2.1 Booking lifecycle is table-dependent
- `restaurantBookings.tableIds` is a jsonb array referencing `restaurantTables.id`.
- `bookingsConflict()` (`restaurant.ts:717`) checks overlapping table reservations — the conflict model is table-centric, not venue-centric.
- Booking status transitions (`pending → confirmed → arrived → seated → completed`) map to a dine-in table service flow.

### 2.2 No generic venue abstraction exists
- No `venues`, `spaces`, or `resources` table exists.
- No generic `bookings` table without the `restaurant_` prefix.
- The deposit and occasion fields are restaurant/dining semantics.

### 2.3 Role permissions are restaurant-domain
- Booking create/update requires `canUseQ(actor) || actor.role === 'waiter'` (`restaurant.ts:1783, 1837`).
- This is the same role model used for table status updates and floor management.

---

## 3. Evidence of Future Reuse Potential

### 3.1 Reuse signals (weak)
- Booking as a concept is generic (appointments, reservations, time-blocked resources).
- A future non-restaurant workspace (e.g., services, salons, clinics) might want similar capability.
- The `q360ModuleRegistry` in `moduleRegistry.ts` has a `services` workspace (disabled) that could theoretically use bookings.

### 3.2 Reuse blockers (strong)
- **No shared schema:** `restaurantBookings` is physically restaurant-prefixed and table-dependent.
- **No resource abstraction:** Reuse would require extracting `tableIds` into a generic `resourceIds` with a `resourceType` discriminator.
- **No generic policy key:** `tables` is the policy module. A generic booking module would need a new policy key, route structure, and frontend surface.
- **UI is co-located:** Booking UI is embedded in `FloorView.tsx`. Extracting it requires splitting the floor view or creating a new booking view.
- **Q integration is restaurant-scoped:** `booking_brief` draft, `upcomingBookingCount` in briefing, and Q evidence types are all Restaurant-specific.

### 3.3 Reuse assessment
**Conclusion: Reuse is theoretically possible but not currently justified.**
- There is **zero evidence** of another workspace requiring bookings today.
- The `services` workspace is `disabled` and has no backend routes or schema.
- Extracting Bookings to a shared core now would be speculative — violating ADR-020’s protected decision: *“Shared capabilities must not be extracted before reuse evidence.”*

---

## 4. Policy Key Decision

### 4.1 Current state
- **Policy key:** `tables` (`restaurantModulePolicies.ts:32`)
- **Category:** Operations
- **Configurable:** true
- **Default enabled:** true
- **Label:** Tables
- **Description:** "Dine-in table assignment and status."

### 4.2 Options evaluated

| Option | Description | Pros | Cons |
|--------|-------------|------|------|
| **A. Keep subordinate to `tables`** | Bookings remain gated by `tables` module toggle. No new policy key. | Minimal change. Matches current UI co-location. No schema migration. | Booking cannot be disabled independently of tables. Semantically imprecise. |
| **B. Create `bookings` policy key** | Add `bookings` to `restaurantModulePolicies.ts` and gate routes on it. | Precise capability model. Allows independent enable/disable. | Requires: new policy entry, route gating change, potential frontend module registration, moduleAccess alignment, and migration of existing data expectations. |
| **C. Extract Booking Core** | Create generic `bookings` schema and shared module. | Maximum reuse. Clean architecture. | Massive scope: new tables, migration, resource abstraction, new routes, new frontend, Q integration rewrite. Violates M5 freeze boundaries. |

### 4.3 Recommended decision
**Option A — Keep bookings subordinate to `tables` for now.**

**Rationale:**
1. Bookings are **physically and logically coupled** to `restaurantTables`. You cannot book without tables.
2. The UI is **co-located** in the Floor view. Disabling tables while keeping bookings would create a broken user experience.
3. No other workspace needs bookings today. Premature extraction violates platform rules.
4. The `tables` policy description says "Dine-in table assignment and status" — bookings are a natural extension of table assignment.
5. **M5.1 module key alignment** already canonicalized `tables` as the floor/booking module. Adding a second key now would conflict with that alignment.

**Future trigger for Option B:**
- When a second workspace (e.g., Services, Salon, Clinic) needs booking capability AND that workspace does NOT use `restaurantTables`, THEN introduce a `bookings` policy key and consider extraction.

---

## 5. Safest Implementation Boundary

### 5.1 What M5 (and M5.x) should NOT do
- Do NOT add a `bookings` policy key to `restaurantModulePolicies.ts`.
- Do NOT create a dedicated `/app/restaurant/bookings` route or module registry entry.
- Do NOT extract `restaurantBookings` to a generic schema.
- Do NOT modify Q integration to use a generic booking abstraction.

### 5.2 What M5 SHOULD do (already done)
- M5.1 aligned `tables` as the canonical module key for floor + booking (`/floor` route).
- Backend booking routes already enforce `isBusinessModuleEnabled('tables')` (verified lines 1760, 1779, 1833).
- ` FloorView.tsx` correctly renders both tables and bookings under the `tables` module.

### 5.3 What future milestones could do
- **M6+ (if services workspace activates):** Evaluate whether to introduce `bookings` as a standalone policy key or keep it subordinate to a generic `resources` module.
- **M7+ (if multi-venue):** Extract `restaurantBookings` → `venueBookings` with `resourceType`/`resourceId` abstraction.

---

## 6. Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Over-extracting bookings too early | Medium (architectural temptation) | High (wasted effort, broken invariants) | **Enforce ADR-020 rule: no extraction without reuse evidence.** |
| Under-documenting booking→tables coupling | Medium | Medium (future confusion) | **This audit document serves as the record.** |
| Customer requests booking-only mode | Low | Low | Redirect to tables module toggle; explain coupling. |
| Services workspace needs bookings | Low | High | Delay until services schema is designed; then evaluate Option B. |

---

## 7. Summary Recommendation

| Question | Answer |
|----------|--------|
| **Current booking ownership** | Restaurant-specific, subordinate to `tables` module |
| **Restaurant-specific behavior** | Yes — table-dependent, dine-in lifecycle, restaurant role model |
| **Future reuse potential** | Low today; possible if Services/Salon workspace activates |
| **Should Booking become Booking Core now?** | **No.** Insufficient evidence. Violates ADR-020. |
| **Required policy key decision** | **Keep `tables` as the canonical policy key for bookings.** |
| **Safest implementation boundary** | Do not add `bookings` policy key. Do not extract schema. Keep FloorView as unified surface. |
